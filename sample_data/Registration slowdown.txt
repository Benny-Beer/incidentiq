INCIDENT REPORT
Date: 2024-09-02 (First day of semester registration)
Reported by: David Okafor, Systems Administrator
Severity: P1
Duration: 2 hours 17 minutes (08:00 UTC - 10:17 UTC)

INCIDENT SUMMARY
University course registration portal became severely degraded at 08:00 UTC,
the exact moment registration opened for 12,400 students. Page load times
exceeded 45 seconds. Estimated 3,800 students unable to register for preferred
courses during the degraded window. Some students missed course enrollment
deadlines entirely.

SYSTEM BACKGROUND
- Registration portal handles ~400 concurrent users normally
- Peak registration day expected 12,400 students over 4-hour window
- New feature deployed 3 days prior: real-time seat availability counter
- Database upgraded from PostgreSQL 13 to PostgreSQL 15 two weeks ago
- Last year registration ran without issues (different system version)

TIMELINE

07:58 UTC - Registration portal opened 2 minutes early for testing
08:00 UTC - Registration officially opened. Student traffic began immediately.
08:01 UTC - Page load times jumped from 0.8s to 12s
08:03 UTC - David Okafor received automated alert: response time exceeded 5s threshold

08:09 UTC - Application server memory at 87% (normal: 45%)

08:44 UTC - Index creation complete

08:47 UTC - System still slow — connection pool exhausted (200/200 connections in use)
08:52 UTC - Connection pool limit increased from 200 to 400
08:58 UTC - Page load times dropped to 0.9s. System recovering.
10:17 UTC - Final stragglers cleared. Incident declared resolved.

ADDITIONAL OBSERVATIONS
- Real-time seat counter feature queries database on every page load and every 10 seconds via polling
- Feature was tested with 50 concurrent users in staging — not tested at 800+ concurrent users
- PostgreSQL 15 migration checklist did not include index verification step
- Scaling from 4 to 8 application servers had no effect because bottleneck was database, not application layer
- Students reported seeing "Your session has expired" errors — likely caused by app server memory pressure
- Financial aid students had priority registration window 08:00-08:30 UTC — most affected group
- Last year's system used cached seat counts updated every 60 seconds, not real-time queries
- Network bandwidth was normal throughout incident
- 23 students submitted formal complaints about missed course enrollment

WHAT WAS NOT INVESTIGATED
- Whether PostgreSQL 15 query planner differences contributed independently of missing index
- Whether application server memory pressure caused additional issues beyond slow responses
- Whether the seat counter polling (every 10s per student) amplified the query load
